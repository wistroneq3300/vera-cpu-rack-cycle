VERA Cycle 測試流程與判定邏輯

這份頁面把腳本從輸入參數、PRE baseline、進入 OS、每一輪 power action，到最後報告判讀的邏輯攤開來。使用者可以依照流程知道「現在在驗什麼」、「什麼情況會停」、「什麼情況會留下 FAIL 但繼續跑」。

1. 開始前：你需要準備什麼

先釐清兩種結果：硬體檢查發現問題，代表結果是 FAIL，但只要腳本有完整執行，該 node 仍可依政策繼續 cycle；腳本沒有完整執行，代表結果不可信，PRE 會 blocked，POST 會停止該 node。

Controller 端

Python 3、Bash、SSH／BMC 連線能力、可寫的 output 目錄，以及能執行所選專案腳本的憑證。正式部署在 Linux；本頁的離線範例不會碰真機。

被測 node

Inventory 中的 BMC／OS 位址與 hostname 必須正確；OS 需能以 root 執行必要檢查。MFT／mst 是硬體檢查期待的 OS 工具，程式不會自動安裝 MFT。

Inventory 最少要有的欄位

欄位用途例子
tray / node組成唯一 node key，例：L105-21R_n1L105-21R,n1
bmc_ip / bmc_hostname驗證 BMC 身分、SEL、電源狀態192.0.2.10 / bmc-n1
os_ip / os_hostname驗證 OS 身分、boot ID、OS 檢查192.0.2.11 / os-n1

2. 輸入什麼：啟動方式

互動式 wizard

不帶參數執行時，程式會依序詢問 project、node、cycle mode、channel，以及用 loops 或 hours 限制執行時間。適合第一次操作或需要人工確認設定的情境。

python3 neutrin_cycle.py

自動化／可重現命令

以下例子對 Neutrino 的 n1 執行 3 輪。--cycle 才會在 PRE 後進入 START 與 Cycle；沒有它只做 PRE，且暫存 PRE evidence 不會保留成 campaign。

python3 neutrin_cycle.py --project neutrino --inventory cycle_inventory_neutrino.csv --node n1 --loops 3 --cycle-mode power_cycle --channel inband --output campaigns --cycle

主要參數

參數可用值／規則影響

--nodeall、node 名稱，或 tray/node；可重複決定本次要做哪些 node。重複 endpoint 會在執行前 blocked。
--loops / --hours二選一，必須是正數到達限制後結束；零輪執行不會被標成 COMPLETE。

3. 一次 Cycle 的總流程

① 輸入驗證參數、inventory、target、limit
② PRE身分、依賴、硬體與 baseline
③ 人工批准接受 finding 與 node 排除
④ START再次驗身分並清理 dmesg／SEL
⑤ Cycle / POSTaction、boot、OS 檢查、證據
⑥ 報告counter、health、HTML、evidence

每一輪只會對仍為 active 的 node 發出 action。某個 node 被停止時，其他 node 仍可繼續；最後只要有 node 未完成或 health 有 FAIL，campaign 就不會被誤判成健康完成。

4. PRE Check：先建立可信的 baseline

驗證每個 endpoint 的身分

對 inventory 中的 BMC／OS（以及有設定的 Lily endpoint）執行 identity command。

  • hostname 必須與 inventory 相符。
  • OS 必須回傳格式正確的 36 字元 boot ID。
  • 身份不符或無法取得時，加入 PRE_BLOCKED／identity finding，不能安全執行 cycle。

驗 root 與 OS 依賴

檢查 id -u 是否為 0，以及必要命令是否存在。缺少套件時會嘗試用 apt 安裝；mst／MFT 不由程式自動安裝。

  • 依賴安裝失敗或工具仍缺少，會留下 package finding。
  • 這些 finding 必須在批准前閱讀；後續 command 仍會以 evidence 呈現成功或失敗。

執行第一次硬體與 OS capture

收集 dmesg、PCI、sensor、SEL、BMC firmware、電源，以及 project config script 的檢查結果。

  • PCI baseline 不可取得時，node 會 blocked，因為後續 PCI 比較沒有可信基準。
  • sensor 問題會保留在 PRE，供 operator review；不會用 shortcut 靜默吃掉 malformed row。

上傳並驗證 hardware script

腳本只上傳一次，之後每次執行前都重新檢查檔案型態、不是 symlink、owner／權限為 root:700，以及 SHA-256。

注意：script_verified 只代表遠端檔案可信，不代表這次 command 已經完整執行。還要通過下一個 execution gate。

判斷 hardware execution 是否完整

硬體命令必須是 transport RETURNED，exit code 與最後一行 RESULT 一致，且只能有一個 terminal RESULT。

  • exit 0 + RESULT|PASS：且沒有 finding，才算完整 PASS。
  • exit 1 + RESULT|FAIL：算完整硬體 FAIL，保留 finding 並 keep-going。
  • NOT_ISSUED、timeout／RESPONSE_LOST、syntax error、缺 final RESULT、結果與 exit 不一致：PRE blocked。

完成 PRE 並等待批准

PRE 會保存原始 evidence，建立 immutable baseline：PCI identity、sensor rows、dmesg fingerprint 與 boot identity。程式列出 runnable 與 excluded node，等待 operator 接受。

Start <RUN_ID> on <N> runnable target(s), accepting the listed findings and exclusions? [y/N]:

5. 批准後：START 不是新的 PRE

批准後，程式建立獨立的 START record，不改寫已審核的 PRE。它會重新驗證 endpoint 身分；如果等待批准期間 OS boot ID 已變，代表原 baseline 可能已過期，會以 identity unsafe 停止，不能悄悄開始。

清理前要有可信 capture

只有 PRE 的 dmesg／SEL capture 有效時才清理。若 PRE capture 失敗，會留下 CLEAR_SKIPPED，保留原 evidence，避免把不完整 baseline 當成已清空。

清理的目的

START 清理 dmesg 與 SEL，讓後續每輪的 delta 能從乾淨的時間點開始；它不會刪除已寫入的 PRE evidence。

6. Cycle 與 POST：每輪實際檢查什麼

Before action

保存本輪 action 前的 OS／BMC identity 與 SEL snapshot，並以 PRE baseline 做比較。這一步是時間窗與 boot 判讀的基準。

送出 power action

依 mode／channel 發送 reboot、power cycle 或 aux cycle。command state 會分成 SENT、RESPONSE_LOST、NOT_ISSUED 或 COMMAND_FAILED。

  • RESPONSE_LOST 不盲目重送；後面用 boot 與 power evidence reconciliation。
  • NOT_ISSUED／COMMAND_FAILED 若 OS boot 維持原值，仍可進 POST，保留 action failure。
  • 如果 action 被拒絕後觀察到額外 boot，加入 UNEXPECTED_BOOT_TRANSITION 並停止該 node，不採用新 boot 當 expected baseline。

等待 OS recovery

輪詢 OS identity，必須看到新的 boot ID；timeout 會停止 node。其他 endpoint 會在 OS recovery 後重新驗證。

POST entry 與硬體 capture

重新檢查 dmesg、PCI inventory、sensor、SEL delta、BMC firmware、chassis power、host power，並再次驗證及執行 hardware script。

  • PCI 是和 PRE 比較，不是只看數量。
  • dmesg 保留完整 raw evidence；AER 多行的 BDF、status、error bit 一起形成 event identity。
  • 正常的 NVMe shutdown timeout 設定訊息不算 failure；真正 I/O timeout、controller down、reset failure 仍會被記錄。

POST 結束 gate

POST 完成前會再次確認 OS identity 沒有在檢查中多重開機。最後才計算 post_complete、boot_confirmed 與 valid_cycle。

8. 怎樣算整場 PASS／FAIL

COMPLETE + PASS

達到 loops／hours 限制、沒有 node 因故停止、health 沒有 FAIL，且至少有有效執行的 cycle。只有報告完整且所有 FAIL gate 都沒有觸發時才成立。

COMPLETE + FAIL

執行限制完成，但有 hardware／dmesg／sensor／power 等 FAIL。這不是假完成；代表流程跑完，但 campaign health 失敗。

INCOMPLETE

有 node 被停止、PRE 沒有可批准的 baseline、零輪 cycle、owner 中斷、rebuild 發現 evidence integrity 問題，或 graceful stop 尚未完成當前流程。

valid_cycle = false

不代表所有 collection 都沒做。它表示沒有同時滿足 boot recovery、stable POST identity、power on、verified script 與 hardware execution complete。

Counter 的意義

Counter意思
attempts嘗試送出的 cycle action，包含 rejected／command failed。
boot_confirmed觀察到預期的 OS boot transition。
completedPOST 到達結尾且 hardware execution 完整。
valid_cyclesrecovered boot、POST identity 穩定、power on、script verified、execution complete 全部成立。

10. 停止、交接與操作後確認

Graceful stop

停止請求只會由 campaign owner 發出，程式會完成目前 POST，不再開始下一輪，也不使用廣泛的 pkill。

python3 neutrin_cycle.py --stop RUN_ID

操作後確認清單

勾選只保存在這個瀏覽器的 local storage，不會寫回 campaign，也不會改變測試結果。
